## Layer responsibilities

**`api/openapi.yaml`** — the *only* source of truth for the HTTP surface. Every REST path, request body, response type, and validation rule starts here. `make generate` turns it into a Go strict-server interface under `internal/api/gen/`.

**`db/migrations/`** — schema evolution as dbmate SQL files. Applied by `dbmate up`.

**`db/queries/*.sql`** — every SQL statement the app issues, annotated with sqlc `-- name:` directives. `make generate` turns them into a Go `Querier` interface under `internal/db/gen/`.

**`internal/server/`** — HTTP handlers. Each resource has its own subpackage (`tenants/`, `kinds/`, `models/`). `server.go` composes the subpackages into a `Server` that implements `apigen.StrictServerInterface`.

**`internal/mcp/`** — MCP tools. Same underlying `dbgen.Querier`, different presentation.

**`cmd/server/main.go`** — the single binary. Opens a pgx pool, constructs the composed HTTP `Server` and the MCP `Server`, mounts both onto one chi router.

**`web/`** — Vite + React + TS. Proxies `/tenants` and `/health` to `:8080` in dev.

## The Endpoint MVVM pattern

Defined in `internal/server/endpoint.go`:

```go
type Endpoint[Req, M, VM, Res any] interface {
    Interact(ctx context.Context, req Req) (M, error)
    Build(m M) VM
    Render(vm VM) Res
}
```

- **Req** — parsed request (usually an oapi-codegen `*RequestObject`).
- **M** — domain model (usually a sqlc row type or slice of them).
- **VM** — view model (a plain struct owned by the endpoint's package).
- **Res** — typed HTTP response (an oapi-codegen `*ResponseObject`).

`server.Run(ctx, endpoint, req)` walks the three steps. The composed `Server` in `internal/server/server.go` looks like:

```go
func (s *Server) ListTenants(ctx context.Context, req apigen.ListTenantsRequestObject) (apigen.ListTenantsResponseObject, error) {
    return Run(ctx, tenants.ListEndpoint{Store: s.q}, req)
}
```

### Why declare a Store per endpoint?

Each endpoint declares a tiny interface with just the querier methods it uses:

```go
type ListStore interface {
    ListTenants(ctx context.Context) ([]dbgen.Tenant, error)
}

type ListEndpoint struct{ Store ListStore }
```

`*dbgen.Queries` satisfies every one of them because sqlc generates every method. The narrow declaration makes each handler easy to test in isolation and makes its data dependencies self-documenting.

## Request flow (REST)

1. chi routes an incoming request to the wrapper generated by oapi-codegen.
2. The wrapper parses the URL, headers, and body into a `*RequestObject`.
3. It calls the matching method on the composed `Server`.
4. `Server` calls `Run(ctx, someEndpoint{Store: s.q}, req)`:
   - `Interact` calls the sqlc querier
   - `Build` maps the row to a view model
   - `Render` returns a typed `*ResponseObject`
5. oapi-codegen serializes the response.

## Request flow (MCP)

1. Claude opens a streamable HTTP session at `/mcp`.
2. Tool calls arrive with typed JSON matching the tool's Input struct.
3. The registered handler runs the SDK's decode → invoke → encode sequence.
4. The handler calls `dbgen.Querier` directly and returns a typed Output struct.

MCP does not currently use the Endpoint interface (tools have their own shape), but it uses the same `dbgen.Querier` so both surfaces see the same rows.

## Code generation boundaries

Two directories are entirely machine-written:

- `internal/api/gen/` from `api/openapi.yaml` (via oapi-codegen, driven by `oapi-codegen.yaml`)
- `internal/db/gen/` from `db/migrations/**` + `db/queries/**` (via sqlc, driven by `sqlc.yaml`)

Both are committed so contributors do not need the codegen tools installed just to build. Regenerate any time you change the corresponding source.
